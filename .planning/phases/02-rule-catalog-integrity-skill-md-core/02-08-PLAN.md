<objective>
Make `tools/check_repo.py --mutation-test` claim only what it proves. Today it prints a single
blended total that counts `skill-token-budget-exceeded` as proven live even though that code's
control state was never clean, so its mutation could not demonstrate any discrimination between
good content and bad. Replace "fires on the mutated copy" with "was silent on the control and fires
on the mutated copy" for every code, and report any code that cannot meet that bar as a separately
labelled, honestly counted case.

Purpose: this is the smallest gap by line count and the largest by category. The repository's
governing constraint is "measured claims or no claims", and `check_repo.py` is the tool that
enforces that constraint on everything else. An overclaim in its own headline number is a reflexive
integrity failure, and 02-REVIEW.md CR-01 proved it experimentally: with the mutation function
replaced by a no-op, the code still reported as firing.

02-07's trim makes the control copy clean, which makes today's printed `21` true by accident. That
is not sufficient. A tool whose honesty is contingent on repository state that can drift is still
the defect, so the fix here is the general one — assert discrimination for every code — and it
stays correct whether or not SKILL.md is under budget.

Output: a mutation mode that measures discrimination, an emptied `KNOWN_OPEN_VIOLATIONS` with a
comment that says why, two corrected docstrings, and 21 codes still covered.

## What `mutation_test()` does today (`:1364-1410`)

1. Copies the repository into a control root, runs `run_all_checks`, filters the result through
   `KNOWN_OPEN_VIOLATIONS`, prints a CONTROL line, and sets `all_ok = False` only on an *unexpected*
   control violation. The control's per-code detail is then discarded when the `with` block exits.
2. For each `(code, description, mutate_fn)` in `MUTATIONS`: fresh scratch copy, apply the mutation,
   `run_all_checks`, then `fired = any(line.split(' ', 1)[0] == code for _, line in violations)`.
3. `fired` → print `mutation-test OK: ...` and add the code to `codes_covered`; else print
   `mutation-test FAIL: ...` and set `all_ok = False`.
4. Reports any code in `ALL_CHECK_CODES` with no registered mutation as a failure.
5. On success prints a single total built from `len(codes_covered)`.

The defect is precisely step 2's `fired`: it answers "does this code fire on the mutated copy",
which for a code already firing on the control is a question with a known answer before the
mutation runs.

## The shape of the fix

The control run is already the per-code pre-state for every mutation — every scratch copy starts
from the same `_copy_repo_subset` of the same tree. So the comparison needs no second run per
mutation: capture the control's set of firing codes once, hoist it out of the `with` block, and
classify each mutation against it.

- silent on control, fires after mutation → **discrimination-proven**.
- fires on control, fires after mutation → **confirmed-fire-only**, counted separately.
- does not fire after mutation → failure, exactly as today.

Measured cost: `--mutation-test` currently runs in about 0.23s wall on this checkout, so nothing
here is performance-sensitive either way.

## `KNOWN_OPEN_VIOLATIONS` today (`:1046-1063`)

`frozenset({'skill-token-budget-exceeded'})`, consulted only by the CONTROL filter. Its own
comment describes it as a "narrow, named allowance" for one fact about one file. After 02-07 the
fact is no longer true, so the allowance is not merely unused — it is a stale hole that would
absorb a genuine future regression of that code into the known-open bucket. 02-REVIEW.md WR-01
proposed re-scoping it to a `(code, subject)` pair; emptying it removes the hole outright, which is
strictly stronger and needs no new filter shape.
