<planner_recommendation>
**Recommended: route (b) — accept the residual for v1 and harden the disclosure. Not route (a).**

This is a reasoned recommendation, not a default. The four grounds:

**1. The measurement history does not support a fifth lever.** Four rounds, three structurally distinct
levers — 03-05's instruction restatement, 03-07's unconditional five-value family line with a presence
gate, 03-11's mechanical self-check ordering re-scan. None reached 87.5%. The one round produced under
a scorer proven not to inflate the rate (03-12, after 03-09's `FAMILY_LINE_WINDOW_CHARS` fix) is both
the lowest figure recorded (30.0%) and 10 points below its own paired baseline (40.0%). The earlier
apparent progress from 45.5% to 60.0% is, by the project's own written assessment, substantially a
scorer artifact. A fifth round of the same family of lever has a weakening evidence base, and the
project's own pre-committed disposition rule already bars another rewording.

**2. Route (a)'s named candidate is architecturally unavailable at v1.** 03-12's Next Phase Readiness
names it precisely: "a post-generation mechanical repair (not just detection) that the skill or a
wrapping tool applies before the response reaches the user, rather than trusting the model's own
re-scan." A skill in the Agent Skills format is Markdown loaded into a model's context. It has no
execution point after generation and cannot intercept or rewrite the model's own output. Anything that
could — a Claude Code hook, a wrapper CLI, an output-style post-processor — is a harness-specific
runtime component, and would break two constraints this project holds as load-bearing and documented:
zero dependencies with one folder and no install step, and cross-harness portability including the
claude.ai upload and the paste-able system prompt channels, neither of which can run a hook at all. So
the residual failure mode is not a lever the project declined to build; it is one the project's own
architecture forecloses. That belongs in the record as a stated scope boundary, not as another failed
attempt.

**3. The structural half of MOD-04 is verified and mechanically held.** `03-VERIFICATION.md` truth 4 is
verified: the classification instruction exists in both modes, states the ordering explicitly, and is
gated on both presence and ordering by two discrimination-proven codes. What fails is a model-behavior
property that no file-reading checker can hold and that three prompt-side levers have not moved. The
shipped artifact is as correct as this project's own tooling can make it.

**4. The honest v1 posture is publication, not iteration.** This repository's governing constraint is
"measured claims or no claims." It has an honest, anchored, reproducible number that happens to be
unflattering. Publishing it with caveats is the behavior the constraint demands. Spending another
live-session budget — twice interrupted by usage limits in prior rounds — on a lever the architecture
forbids would be the less honest choice, not the more rigorous one.

**What route (b) is not.** It is not closing MOD-04. The checkbox stays unchecked, `WINDOWS.md` entry 8
stays `waived` rather than `fixed`, and the record states explicitly that this is an accepted, disclosed
residual and not a satisfied requirement. It is reversible: reopening entry 8 is a one-line ledger
operation, and the decision record names the evidence that would justify it.

**What would change the recommendation.** Route (a) becomes worth a fifth round if, and only if, the
project decides to add a distribution channel that can run code after generation — which is a ROADMAP
and PROJECT.md scope change, owned by a milestone decision rather than by this phase.
</planner_recommendation>

sampling-noise caveat stated alongside rather than instead.
