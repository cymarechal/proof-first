<objective>
Close CR-01 -- the one gap `04-VERIFICATION.md` carries as `failed`. `check_plugin_manifest_invalid`
enforces `PLUGIN_REQUIRED_KEYS` against `.claude-plugin/plugin.json`'s top-level object and nothing
else; `.claude-plugin/marketplace.json`'s nested `plugins[0]` entry is inspected for its `source`
field alone. The function's docstring says it asserts that both manifests have "every required key
present". For the marketplace entry that is false, and the marketplace entry is the object
`claude plugin marketplace add` actually reads.

Purpose: this checker is the phase's sole mechanical proof that the manifest driving the plugin
install route is well-formed, so DIST-02's structural evidence currently rests on a proof that does
not hold for the fields it claims to hold. Worse for the project's own standard: plan 04-10's stated
purpose last round was closing exactly this defect class -- a tool overstating what it checks -- in
exactly this function, and it shipped without catching this instance. A repository whose argument is
that a claim is worth what its evidence is worth cannot close that gap a second time by fixing one
more instance and hoping. So this plan fixes the instance and then makes the class mechanically
unable to recur here: an exhaustive assertion that every key in the required set, at every position
the docstring claims to cover, actually makes the code fire.

Output: required-key presence enforced on the marketplace plugin entry, an eighteen-cell self-test
matrix proving it key by key and position by position, a second real-file mutation registered for
`plugin-manifest-invalid`, an equality guard on the five hand-duplicated distribution fields, two
docstrings that claim exactly what is enforced, and one punctuation repair in a shipped worked
example. No new violation code; the discrimination-proven total stays at 47.
</objective>

## Trust Boundaries

Stated honestly: this plan's entire surface is a standard-library Python script reading two
version-controlled JSON files and one Markdown file from its own repository, offline. There is no
network call, no subprocess, no user-supplied input, no deserialization of an executable format, no
credential, no database and no served endpoint. Most STRIDE categories therefore have no component
to attach to here, and inventing one would be the same failure this repository's own standard
forbids.

| Boundary | Description |
|----------|-------------|
| contributor commit → CI checker | A contributor (or an attacker with PR access) authors `.claude-plugin/*.json`; `tools/check_repo.py` parses it in GitHub Actions. The manifest content is the only externally-authored input this plan's code reads. |
| repository → plugin harness | `.claude-plugin/marketplace.json` is read by `claude plugin marketplace add` on an end user's machine. This plan does not execute that path; it only asserts the manifest's shape before publication. |
| *(no boundary)* | No network, no subprocess, no environment variable, no filesystem write outside `tempfile.TemporaryDirectory()`, no package-manager install. The surface is genuinely empty here, and is recorded as empty rather than padded. |
