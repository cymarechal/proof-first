<objective>
Make every install claim in `README.md` true of a bare clone, and register the one narrow mechanical
fact that would have caught the false one.

Purpose: routes 1 and 2 are both gated on an unpublished `<owner>/<repo>`, so routes 3 and 4 are the
entire usable install surface today — and route 3 does not work as written. The README promises it
runs from a local clone and then gives it in full as "select it through `/config`", with no step in
between. `output-styles/` at this repository's root is the location a plugin ships an output style
from; Claude Code scans `~/.claude/output-styles/` and a project's `.claude/output-styles/`, and this
repository populates neither. The route's real enabling mechanism is route 2, the route the README
itself correctly says will not resolve until publication. So half the usable install surface is wrong,
in the section a prospective evaluator acts on first.

The repository already had to close CR-01 for a checker that claimed more coverage than it had. The
answer here is not another presence check wearing an executability name — it is one narrowly named
code that asserts exactly the fact that failed, plus a README that states the missing step and is
honest about which link in the chain this environment has not observed.

Output: a route 3 a reader can follow, a preamble whose today-runnable claims match it, a 48th
discrimination-proven violation code proven red-then-green against the real `README.md`, four folded-in
credibility defects, and one tracked unrun verification.
</objective>

<mechanisability_assessment>
`04-UAT.md` asks whether route executability is mechanically checkable from a clean clone. It is not,
and one necessary condition of it is. This plan registers the condition and refuses the claim.

**Refused: a code asserting a route works.** Proving route 3 works means observing Claude Code load a
file. That is another product's runtime, behind an interactive picker, in an environment this
repository does not drive. A code named `readme-route-executable`, or any name a reader would read
that way, would assert coverage it does not have — the precise failure CR-01 closed for
`marketplace.json`, and the same failure `readme-install-path-missing`'s own declared ceiling already
admits to ("it does not assert the command is correct, that it resolves"). Do not add it.

**Registered: a code asserting the destination is named.** That README names the output-style file as
a route while naming neither directory the harness scans is a fact about this repository's own file.
It needs no network, no harness and no publication to check, and it is exactly the fact that was false
at HEAD — verified this session: four occurrences of the output-style path, zero occurrences of either
destination. A code asserting it would have failed the build on the commit that introduced the claim.

The honesty of the code rests on its name and its declared ceiling, not on its cleverness. It is named
for the string it looks for. Its docstring must state that it asserts the README tells the reader where
the file has to go, and that it asserts nothing about whether the copy succeeds, whether Claude Code
lists the style, whether the command is correct, or whether any other route is executable.

The residual — that a human still has to observe the harness listing the style once — is filed as a
`.planning/WINDOWS.md` unrun-verify entry in Task 3, next to the two entries already carrying the same
class of ceiling.
</mechanisability_assessment>
